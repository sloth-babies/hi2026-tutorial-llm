# 仕様判断ログ

更新日: 2026-09-04

## D-001: 1ページ構成を採用する

**判断**: 初期版はコース3専用の1ページサイトとする。

**理由**: 対象は単一コースであり、参加者が概要から演習へ短い導線で進むことが重要。複数ページ化は教材量や講師情報が増えた時点で検討する。

## D-002: 開催前と開催後の両方を対象にする

**判断**: イベント案内と教材アーカイブを兼ねる。

**理由**: 開催前は参加準備、開催後はColab・資料の再利用が主目的になる。開催前だけの文面や一時的なカウントダウンは初期版では避ける。

## D-003: Colabを最重要導線にする

**判断**: ファーストビューに演習用ColabへのCTAを置く。

**理由**: このサイトの主な利用行動は「講習内容を知り、演習を開始すること」。RAG用Colabを現在の主要リソースとし、後からリンクを追加できるデータ構造にする。

## D-004: 資料は掲載するが、主役にしない

**判断**: PDFは「演習・資料」セクションに置く。

**理由**: 参加者や受講後の閲覧者には有用だが、最初の行動はColabへの移動であるため。長いPDFをページ内に埋め込まず、ダウンロードまたは別タブで開くリンクにする。

## D-005: 講師紹介は掲載する

**判断**: 2名の講師紹介を掲載し、ファム フーロンのホームページへリンクする。

**理由**: コースの専門性と信頼性を伝えられる。略歴を長く転載せず、所属・専門分野・短い紹介に絞る。

## D-006: 公式サイトの内容を再掲載しすぎない

**判断**: 学会情報は要点だけ載せ、詳細は公式サイトへリンクする。

**理由**: 公式情報の二重管理を避け、日時や会場変更時の不整合を減らすため。

## D-007: 追加演習は後からデータ追加で対応する

**判断**: RAG以外の演習リンクは、URLが提供された時点で追加する。

**理由**: 現在未確定のリンクを仮置きしない。初期実装のレイアウトは、演習項目が増えても破綻しないリスト形式にする。

## D-008: 実装前にドキュメントを作る

**判断**: 仕様・掲載情報・判断ログ・更新手順を先にリポジトリへ残す。

**理由**: 新しい会話で再開した場合でも、目的・出典・保留事項・更新方法をすぐ確認できるようにする。

## D-009: GitHub ActionsでGitHub Pagesへ公開する

**判断**: `main`へのpushをトリガーにAstroをビルドし、GitHub Pagesへ自動デプロイする。

**理由**: Astroはビルドが必要であり、生成済みの`dist`を専用ブランチへ手動管理するより、ソースと生成物を分離できるActions方式が適している。workflow_dispatchによる手動再実行も用意する。
